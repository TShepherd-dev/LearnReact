Page state & loading: empty, error, retry

Lesson 0008 built the Home page's happy path: useEffect calls mockHome(), the promise resolves, widgets get props. Today we finish the job — everything that happens when the promise doesn't cooperate. By the end you'll have a page that can sit in any of four states: loading, success, empty, or error-with-retry.

Recall first (from Lesson 0008)

Before we add the error path, re-retrieve the punchline you met on the mock contract:

Why does the mock have to match the real API's shape exactly?

So the component never knows the data came from a file — going live later is a one-line import swap, not a rewrite. Lesson 0008 built the shape-match; today we extend that honesty to failure.

The one idea

A React page that loads data owns four states — loading, success, empty, error — and they all flow from one function it can call again. Retry isn't a navigation or a plugin; it's just calling that function once more. (react.dev · Synchronizing with Effects)

Read the real file

Open src/store/account.js in the source app and find getMetrics:

getMetrics({ commit }) {
  commit('setMetricsLoading', true);
  return api.get('api/user/getMetrics').then((data) => {
    if (data.Output) commit('setMetrics', data.Output);
  });
  // notice: NO .catch
}

and src/api/axios.config.js — the response interceptor:

// on HTTP 500:
safeShowGrowlMessage('warning',
  'An application error occurred - please refresh...');
// on HTTP 401:
//  silently retry the same request after 2 seconds
return new Promise((resolve, reject) => {
  setTimeout(() => { resolve(axios(error.config)); }, 2000);
});

Spot the pattern: in Vue, the page never sees its own failure. The store commits a loading flag and returns; if the request fails, the axios interceptor catches it centrally — a growl banner here, a silent 401 retry there. Per-page error state simply doesn't exist, because the framework route is the interceptor.

The shift

React has no central interceptor by default. A rejected promise comes back to the page that created it, and the page decides what to render. The Vue code kept loading in the store and failure in the interceptor; the React page keeps all four states in local state.

React · Home.jsx (ported)

const [payload, setPayload] = useState(null);
const [isLoading, setIsLoading] = useState(true);
const [error, setError] = useState(null);

const load = () => {
  setIsLoading(true);
  setError(null);
  mockHome()
    .then(setPayload)
    .catch(setError)
    .finally(() => setIsLoading(false));
};
useEffect(() => { load(); }, []);

if (isLoading) return <p>Loading…</p>;
if (error) return (
  <div>
    <p>Something went wrong.</p>
    <button onClick={load}>Retry</button>
  </div>
);
if (!payload.whatsHotModules.length) return (
  <p>No "what's hot" modules yet.</p>
);
return ( /* the widgets, as before */ );

Three habits worth naming:

  • One load function. The effect calls it on mount; the Retry button calls it on click. The fetch exists once, not twice — that's all retry is.
  • Reset before you ask. load starts by clearing error and setting isLoading true, so a retry shows Loading again, not the stale error.
  • The early-return order. Loading → Error → Empty → Content. Each state is a return that ends the render before the next branch.

The mock must be able to fail

Look at your src/mock/api.js: mockHome can only resolve. If it can never reject, the error and retry branches you just wrote are dead code — fiction you can't test. The golden rule from Lesson 0008 extends: the mock fulfills the same contract as the real API, including failure.

export const mockHome = (opts) =>
  new Promise((resolve, reject) => {
    setTimeout(() => {
      if (opts && opts.fail) {
        reject(new Error('network down'));
        return;
      }
      resolve({ /* the same shape as before */ });
    }, 400);
  });

Now you can prove the error path exists: call mockHome({ fail: true }) and watch the Retry button appear — exactly the code your future deploy-time self will thank you for.

Why this matters for your mission

The app shell and Home screen you're porting are the visible slice — and every subsequent slice (My Training, Search, Catalogue) loads data the same way. Empty states are a real UX deliverable interviewers probe, and the “who owns the failure?” question is a classic React-vs-Vue-mental-model discussion.

One honest caveat, per Lesson 0006: production React apps usually don't hand-roll this in an effect — TanStack Query's useQuery gives you loading/empty/error/retry out of the box. But the states are the same; you're learning the machine before switching to one that drives it for you. (react.dev warns against hand-rolled fetching in shipped apps — we do it here precisely because it's the clearest way to see the machine.)
