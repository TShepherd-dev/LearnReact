From JSX to TSX: types define the component contract

Every component you've built in demo-react-app has an implicit contract: Pagination quietly expects start, total, pageSize and onPage, but nothing stops a parent from passing total="twenty". This lesson converts that silent agreement into a checked, compiler-enforced one — by renaming your JSX files to TSX and typing the props, the reducer, and the route table. From your C# background this is instantly familiar: it's the compiler catching bugs before the browser runs.

The one idea that unlocks everything

TSX is the same JSX file with a compile-time type checker. Nothing about how the app runs changes — but the shape of what flows between components (props, state, dispatch, routes) becomes explicit and verified before you press F5. (typescriptlang.org)

TypeScript does not change React. It changes when you find out you got a contract wrong: from a confusing runtime undefined in the browser to a red squiggle and a tsc error in the editor.

What TSX adds — and what it never changes

  • Adds: type annotations on props, state, variables, function signatures, exports. Your editor shows the expected shape; wrong usage becomes a compile error.
  • Adds: type-only imports (import type) for types that don't exist at runtime.
  • Does not change: the bundle size, the rendering, the lifecycle, or how the app behaves. Types are erased at build time.
  • Does not add: data fetching, routing, or any new capability. It only checks the code you already wrote.

Read the real file — Pagination.jsx

Open demo-react-app/src/components/Pagination.jsx (which we translated from the source pagination.vue back in lesson 0003). It declares four props by destructuring:

JSX · Pagination.jsx today

export default function Pagination({ start, total, pageSize, onPage }) {
  const totalPages = Math.ceil(total / pageSize);
  const next = () => {
    if (start === totalPages) return;
    onPage(start + 1);
  };
  // ...
}

Nothing enforces that total is a number, that pageSize isn't zero, or that onPage is even a function. If Home.jsx passes total="100" by mistake, Math.ceil("100" / 13) happens to work — until the day it doesn't, and your pagination silently breaks with no error at all.

Translate it

JSX · Pagination.jsx (before)

export default function Pagination(
  { start, total, pageSize, onPage }
) {
  const totalPages = Math.ceil(total / pageSize);
  const next = () => {
    if (start === totalPages) return;
    onPage(start + 1);
  };
  const prev = () => {
    if (start === 1) return;
    onPage(start - 1);
  };
  return (...buttons...);
}

TSX · Pagination.tsx (after)

type PaginationProps = {
  start: number;
  total: number;
  pageSize: number;
  onPage: (page: number) => void;
};

export default function Pagination(
  { start, total, pageSize, onPage }: PaginationProps
) {
  const totalPages = Math.ceil(total / pageSize);
  const next = () => {
    if (start === totalPages) return;
    onPage(start + 1);
  };
  const prev = () => {
    if (start === 1) return;
    onPage(start - 1);
  };
  return (...buttons...);
}

Read the C# in it:

  • type PaginationProps = {...} — a property contract, like a record/interface. <Pagination total="one-hundred" /> no longer compiles.
  • (page: number) => void — how a function prop is typed: write the function's argument list and return type in brackets, then => void. onPage takes exactly a number and returns nothing. This is the killer: a callback that's typed catches the mistake at the call site, in the parent, along with the message "Type 'string' is not assignable to type 'number'".
  • Same runtime code — the type annotations are stripped at build time. The browser runs identical JavaScript.

Type the state and the reducer too

Now the shell context you built in lesson 0006 — ShellCtxProvider.jsx. In JSX, shellReducer accepts any action object and returns anything. To type the actions, React and TypeScript use a discriminated union:

JSX · ShellCtxProvider.jsx (before)

const initialShellState = {
  header: true, showSideMenu: false,
  isSearchOpen: false, isMobileMenuOpen: false,
};
function shellReducer(state, action) {
  switch (action.type) {
    case 'showHeader':
      return { ...state, header: true };
    case 'setSideMenu':
      return { ...state, showSideMenu: action.show };
    case 'toggleSearch':
      return { ...state, isSearchOpen: action.open,
               isMobileMenuOpen: false };
    default: throw Error('Unknown: ' + action.type);
  }
}

TSX · ShellCtxProvider.tsx (after)

type ShellState = {
  header: boolean;
  showSideMenu: boolean;
  isSearchOpen: boolean;
  isMobileMenuOpen: boolean;
};

type ShellAction =
  | { type: 'showHeader' }
  | { type: 'setSideMenu'; show: boolean }
  | { type: 'toggleSearch'; open: boolean };

const initialShellState: ShellState = {
  header: true, showSideMenu: false,
  isSearchOpen: false, isMobileMenuOpen: false,
};

function shellReducer(
  state: ShellState, action: ShellAction
): ShellState {
  switch (action.type) {
    case 'showHeader':      return { ...state, header: true };
    case 'setSideMenu':     return { ...state, showSideMenu: action.show };
    case 'toggleSearch':
      return { ...state, isSearchOpen: action.open,
               isMobileMenuOpen: false };
    default: throw Error('Unknown: ' + action.type);
  }
}

What "discriminated union" means, plainly

A union is a type that can be one of several shapes — the C# equivalent is a collection of records, or an F# union, where each option is a distinct object type. "Discriminated" means there is a field you can look at to tell which shape you're holding. Here that field is type, and each member lists its own extra fields:

Action valueAllowed extra fieldsExample that compiles
{ type: 'showHeader' }nonedispatch({ type: 'showHeader' })
{ type: 'setSideMenu' }must include show: booleandispatch({ type: 'setSideMenu', show: true })
{ type: 'toggleSearch' }must include open: booleandispatch({ type: 'toggleSearch', open: false })

This is what the switch relies on. Inside the case 'setSideMenu': arm, TypeScript narrows action to just that member — so action.show is typed boolean there, and action.show inside a different case is a compile error (that shape doesn't have it). The union type is what you hook up to useReducer:

const [state, dispatch] = useReducer(shellReducer, initialShellState);
// dispatch only accepts ShellAction — every consumer is checked too.

What TypeScript now guarantees for you:

  • dispatch({ type: 'setSideMenu' }) without show is a compile error — the setSideMenu arm requires show: boolean.
  • dispatch({ type: 'shoHeader' }) (typo!) is a compile error — only the three listed types exist.
  • Inside each case, action is narrowed: action.show exists only in the 'setSideMenu' arm. The discriminated union does the narrowing for free.
  • The useReducer return infers dispatch accepting only ShellAction — every consumer gets the check too.

How many unions? Where do they live?

The honest scale: one union per reducer — not per app, not per component. A union is just a type written in a file; you export it and import it wherever that reducer's dispatch is used. Think of an app as a set of state slices (the Vuex modules you know: shell, account, catalogue, myTraining…). Each slice that uses useReducer owns one State type and one Action union:

Slice · Shell context (this lesson)

type ShellState = { header: boolean; ... };
type ShellAction =
  | { type: 'showHeader' }
  | { type: 'setSideMenu'; show: boolean }
  | { type: 'toggleSearch'; open: boolean };
// useReducer(shellReducer, initialShellState)

Slice · A second context (example)

type AccountState = { user: User | null; ... };
type AccountAction =
  | { type: 'setUser'; user: User }
  | { type: 'logout' };
// a SEPARATE union for a SEPARATE
// reducer/slice. Two slices, two unions.

The two panels are not connected — that's the point. Only the messages that concern one reducer belong in its union. If you later find two reducers need identical actions, that's a signal to lift the shared slice up (one parent reducer) rather than duplicate the vocabulary.

Components don't "own" unions, they consume them. A component calls dispatch with a member of ShellAction, or receives a User typed via a slice's State. The union is the contract between the reducer and every dispatcher.

What the union is really for

Three jobs, in order of importance:

  1. A closed vocabulary of messages. It answers "what are all the ways this slice's state can change?" — the same question Vuex answers by convention with mutation/action name strings, but now the compiler knows the full list. Veto a typo before runtime.
  2. Payload per message. Each member declares its own fields. setSideMenu requires show; showHeader can't have random extra data slip in.
  3. Exhaustiveness. Add a new member to the union and TypeScript flags every switch missing a case for it. This is how a new action retrofits every reducer — instead of hunting string literals.

How to migrate the Vue code to React, with types

The Vue source has no type safety anywhere — Vue 2 + plain JS, like your demo-react-app at this moment. So the "migration with types" is not one big rewrite; it's a sequence of tiny, verifiable steps. Do them in this exact order:

  1. Install the compiler. In demo-react-app: npm i -D typescript. (The React type packages @types/react and @types/react-dom are already installed in this project.)
  2. Add the tsconfig. Create demo-react-app/tsconfig.json at the project root with the settings below. These are the Vite React template defaults, explained inline.
  3. Prove the check runs. Run npx tsc --noEmit. With only .jsx files and allowJs: true, it should pass with no errors — this is your baseline.
  4. Convert the leaf contract first. Rename src/components/Pagination.jsx → src/components/Pagination.tsx and add the PaginationProps type. Because the component previously had no type, TypeScript now reports any mismatch at every call site — including inside Home.jsx, which passes start={count} where count is a number. Run npx tsc --noEmit again.
  5. Type the state logic. Rename ShellCtxProvider.jsx → ShellCtxProvider.tsx, add ShellState and ShellAction from this lesson. Now ShellTopMenu.jsx’s dispatch({ type: 'setSideMenu', show: ... }) is checked automatically. Run tsc again.
  6. Type the route table. Rename ShellRouteTable.jsx → ShellRouteTable.tsx and type the array as AppRoute[] (see the reference). Now ShellLayout’s displayLocation === 'topmenu' filter is spelled checked. Run tsc one final time.
  7. Stop. Leave every other file as .jsx. You have converted the three places contracts live — component props, reducer actions, and the route data — and the rest of the app still runs. Convert more later, one file at a time, whenever you touch them.

Shell · tsconfig.json (Vite React defaults, annotated)

{
  "compilerOptions": {
    "target": "ES2022",            // modern JS output target
    "lib": ["ES2022", "DOM", "DOM.Iterable"],   // browser + JS types available
    "module": "ESNext",            // ESM modules (Vite)
    "moduleResolution": "bundler", // how imports resolve (Vite/bundler style)
    "jsx": "react-jsx",            // automatic JSX runtime — no "import React"
    "noEmit": true,                // tsc only checks; Vite still does the build
    "strict": true,                // all strict checks on (you want this)
    "allowJs": true,               // existing .jsx files still compile
    "skipLibCheck": true,          // skip checking .d.ts inside node_modules
    "types": ["vite/client"],      // Vite env types (import.meta.env)
    "isolatedModules": true,       // per-file transpile safety (Vite requirement)
    "verbatimModuleSyntax": true   // type-only imports must use "import type"
  },
  "include": ["src"]
}

The allowJs: true flag is the hero of an incremental migration: you can rename Pagination.jsx → Pagination.tsx and type it, while every other file stays .jsx and still runs. Convert one file at a time, type the public boundary (props), and let the compiler tell you every call site that needs updating.
