Auth & routing: the guard becomes a component

The app shell and the Home page you've ported so far are the visible app. Today you port the door: the auth gate. The source app opens its door with a router.beforeEach hook backed by a Vuex bffAuth store; by the end of this lesson you'll have an equivalent door in React — a <RequireAuth> component backed by a useAuth context — with a mock BFF standing in for the real identity server.

Recall first (Lesson 0009’s punchline)

Why does the Retry button in the Home page call the same load() that the effect calls?

One fetch, one place — retry is just running that one fetch again. The effect and the button share load(), so retry is not a new code path, it is the same code path re-invoked.

The one idea

A Vue router guard intercepts navigation. A React “guard” is a component that returns what should render next: <Navigate> to the login page for guests, or <Outlet /> to let the protected children through. Deciding what renders is rendering. (reactrouter.com · data routers, react.dev · components)

Read the real file

Open src/routers/core.js in the source app and find the auth gate inside router.beforeEach:

// inside router.beforeEach(to, from, next)
const authRequired = to.matched.some(r => !r.meta.isPublic);

if (authRequired && !store.getters['account/getCurrentUser']) {
  store.dispatch('bffAuth/login'); // full-page redirect to the identity server
  return next(false);              // this navigation never happens
}
// remember where the user wanted to go, for the return trip
sessionStorage.setItem('requestedPath', to.fullPath);

Then open src/store/bffAuth.js and look at login() — the “login page” is not a page the app builds:

login() {
  // PKCE then: present the auth server's login page
  const params = { client_id,
    response_type: 'code',
    scope: 'openid profile email offline_access',
    redirect_uri: window.location.origin + '/auth-callback',
    code_challenge, code_challenge_method: 'S256' };
  window.location.href =
    authorityUrl + '/connect/authorize?' + new URLSearchParams(params);
}

And src/views/AuthLogin.vue is barely a file:

<template><div></div></template>
<script>
export default {
  created() { this.$store.dispatch('bffAuth/login'); }
};
</script>

Three facts worth naming before we translate:

  • The guard is where the decision lives. “Is there a user?” is asked once, imperatively, at every navigation — and the answer is enforced by cancelling the navigation and redirecting the whole page.
  • The return trip is remembered by hand. The guard stashes the intended URL in sessionStorage['requestedPath'] and the auth-callback handler reads it back after login.
  • Login is a full-page redirect. The Vue app never renders a login form; bffAuth/login() sends the browser to the identity server, which redirects back to /auth-callback with a ?code=.

The shift

React Router has no global beforeEach. Instead of a hook that runs around a navigation, you place a component in the route tree that wraps the protected routes. Its render is the guard.

Vue · the source app

// guard in the router
if (authRequired && !currentUser) {
  dispatch('bffAuth/login');
  return next(false);
}
sessionStorage.setItem('requestedPath', to.fullPath);

// Vuex store bffAuth: reactive auth state
// AuthLogin.vue: created() dispatch('bffAuth/login')

React · RequireAuth.jsx

function RequireAuth() {
  const { user } = useAuth();
  const location = useLocation();

  if (!user) {
    return <Navigate to="/login"
      state={{ from: location }}
      replace />;
  }
  return <Outlet />;
}

Three consequences of moving the guard from the router into a component:

  • It reacts to auth changes. RequireAuth is just a component; it re-renders whenever context changes. When the user logs in, every guarded route becomes reachable without one more navigation. Vue needed the guard to cancel a navigation; React lets the tree render the answer on its own.
  • There is no way for guard and login to disagree. Both read the same useAuth().
  • Guests still get a URL, not a dead end. <Navigate to="/login" replace /> writes a fresh history entry where the next(false) + window.location.href pair would have torn the SPA out of the page.

Where the auth state lives

The Vuex bffAuth module is a store of reactive auth state. React’s equivalent is a context provider at the root — the same pattern you met in Lesson 0006, applied to auth instead of the shell.

// src/auth/AuthProvider.jsx
export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);
  const [isBootstrapping, setIsBootstrapping] = useState(true);

  useEffect(() => {
    // mirrors App.vue's mounted() boot: ask the BFF "is there a session?"
    mockBff.getSession()
      .then((s) => s.isAuthenticated && setUser(s.user))
      .catch(() => {})                 // no session - stay logged out
      .finally(() => setIsBootstrapping(false));
  }, []);

  const login = async () => setUser(await mockBff.login());
  const logout = async () => { await mockBff.logout(); setUser(null); };

  if (isBootstrapping) return <Splash />;   // no flash of protected UI

  return (
    <AuthContext.Provider value={{ user, login, logout }}>
      {children}
    </AuthContext.Provider>
  );
}

Two details worth naming:

  • The boot gate. The source app waits for initApp while a splash shows (SHOW_LOADING). Here, AuthProvider holds isBootstrapping and renders <Splash /> until getSession() answers. Until that resolves, we must not render protected routes — a logged-out user would see a flash of the shell before the redirect.
  • The mock is the BFF. The real endpoints are /bff/getSession-style calls; in a real deployment login() would set window.location.href to the identity server, exactly like the Vue code. The demo resolves a fake user instead. Mirrors the golden rule from Lessons 0008/0009: the mock returns the real shape, so going live later is a one-line import swap.

Wiring the tree

In App.jsx, public routes sit outside the guard; everything under the shell sits inside it:

// App.jsx
<ShellCtxProvider>
  <BrowserRouter>
    <Routes>
      <Route path="/login" element={<Login />} />
      <Route path="/auth-logout" element={<LoggedOut />} />

      <Route element={<RequireAuth />}>
        <Route element={<ShellLayout />}>
          <Route index element={<Home />} />
          <Route path="my-training" element={<MyTraining />} />
          {/* ... the rest of the protected app ... */}
        </Route>
      </Route>
    </Routes>
  </BrowserRouter>
</ShellCtxProvider>

meta.isPublic from the Vue route table maps to position in the tree: routes for guests are siblings of the guard, routes for users are its children. One route tree still drives everything — same idea as Lesson 0005’s menu-from-routes.

The return trip

The source guard saved the destination in sessionStorage['requestedPath']; the auth-callback handler read it back and redirected. React carries it beside the redirect, as location state:

// Login.jsx
const { user, login } = useAuth();
const location = useLocation();
const navigate = useNavigate();

const from = location.state?.from?.pathname ?? '/';

useEffect(() => { if (user) navigate(from, { replace: true }); }, [user]);

return <button onClick={login}>Sign in</button>;

Why replace: true? The /login entry was pushed by the guard’s redirect; we swap it for the originally intended page so the Back button goes to the page before login, not back to the form. Exactly what the official React Router auth example does (examples/auth).

The permission ladder (a forward pointer)

The source guard does more than "is there a user?" — routes carry meta.allowedPermissions and the guard checks them against the user’s groups, redirecting to a /permission page. That maps onto the same pattern: a sibling component like <RequirePermission allowed="user.mustBeAManager"> that either renders <Outlet /> or <Navigate to="/permission" replace />. Worth holding for a lesson of its own; the shape you’re learning today is the shape it will use.

And a warning straight from the source app’s own comment on those permissions: they exist only to control UI route access within the browser — the API does its own, real checks. The React guard is the same: it steers people, it does not protect data.

Rules to remember

  • A guard is a component, not a hook around navigation: <Navigate> or <Outlet />.
  • Public = outside the auth layout route; protected = inside it.
  • Carry the return destination in location state, not sessionStorage — and replace on both sides so Back skips /login.
  • Hold one auth state in context so the guard, the login page and the logout page can never disagree.
  • Render a boot/splash until the session check answers — protected UI must never flash.
  • Client redirects are UX, not security; the identity server and the BFF enforce the real boundary.

  6. Run npm run dev and prove every leg of the trip: logged-out visit to /my-training lands on /login; sign in drops you back on /my-training; the Back button does not return to /login; signing out lands on /auth-logout; and reloading a protected URL while logged in never flashes the shell.
