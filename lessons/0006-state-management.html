State management: what replaces Vuex

Every lesson so far touched the store — mapMutations("catalogue", ...), mapActions("myTraining", ...), $store.state.isMobileNavBeingUsed. Now the big question you'd hit on day one of the port: what replaces the Vuex store itself? By the end of this lesson you'll be able to read any source-app store module and translate it into React state-and-context code, from memory.

The mental-model shift

Vuex is one global store outside your components that everything reaches into. React has no store object — state lives in components, and "global" state is just state lifted to a provider near the top and shared down via Context. (react.dev)

That's the whole trick. Vuex makes the store a magical global; React makes you own it — literally, as component state in a provider. The Vuex concepts don't vanish; they translate:

  • module state → the initial state object in a provider
  • mutations + commit() → a useReducer and its dispatch()
  • actions → plain functions in the provider that call dispatch
  • getters → values derived during render (no cache to buy you anything)
  • mapState/mapGetters/mapActions/mapMutations → a hook like useShell()

Read the real file

Open src/store/shell.js — a tiny, self-contained, namespaced: true module. It owns shell UI state: header, footer, isMobileMenuOpen, isProfileDropdownOpen, isSearchOpen, notificationCount. And a single async action, getUnreadCounts, which calls api.get(...) then commits counts.

Now look at how views consume it. In src/views/Home.vue you'll find:

computed: {
  ...mapGetters("account", ["getCurrentUser", "isManager"]),
  ...mapState("account", ["metrics", "isMetricsLoading"]),
  ...mapState("catalogue", ["parentTags", "isParentTagLoading"]),
},
methods: {
  ...mapActions("shell", ["toggleCacheListing"]),
  ...mapMutations("catalogue", ["setParentTagLoading"]),
}
Vuex reaches into components via these map-helpers. React turns this inside out: the state lives in the tree (a provider), and components read it with a hook.

Translate it

Vue · store/shell.js (abridged)

const state = {
  header: false, isSearchOpen: false,
  isMobileMenuOpen: false, notificationCount: 0
};
const mutations = {
  showHeader(s) { s.header = true },
  toggleSearch(s, open) { s.isSearchOpen = open }
};
const actions = {
  toggleSearch({ commit }, open) {
    commit('toggleSearch', open);
    commit('toggleMobileMenu', false);
  },
  async getUnreadCounts({ commit, rootGetters }) {
    const user = rootGetters['account/getCurrentUser'];
    const data = await api.get(`api/user/getUnreadCounts/${user.UserId}`);
    commit('setNotificationCount', data.Output.Notifications);
  }
};
export default { namespaced: true, state, mutations, actions }

React · ShellContext.jsx (translated)

const ShellCtx = createContext(null);
const ShellDispatchCtx = createContext(null);

function shellReducer(state, action) {
  switch (action.type) {
    case 'showHeader':    return { ...state, header: true };
    case 'toggleSearch':
      return { ...state, isSearchOpen: action.open,
               isMobileMenuOpen: false };
    default: throw Error('Unknown: ' + action.type);
  }
}

export function ShellProvider({ children }) {
  const [state, dispatch] = useReducer(
    shellReducer, initialShellState);
  return (
    <ShellCtx value={state}>
      <ShellDispatchCtx value={dispatch}>
        {children}
      </ShellDispatchCtx>
    </ShellCtx>
  );
}
export const useShell = () => useContext(ShellCtx);
export const useShellDispatch = () => useContext(ShellDispatchCtx);

Spot the patterns:

  • state + mutations → one reducer. Each mutation becomes a case; commit(name, payload) becomes dispatch({type, ...payload}). The reducer returns new state every time — React needs fresh references to re-render.
  • actions → functions in the provider. Sync orchestration (one commit triggering others) becomes a function that calls dispatch a few times.
  • mapState/mapActions → custom hooks. useShell() reads state, useShellDispatch() reads dispatch — this is your replacement for the map-helpers.
  • The async part is not store state. In 2026, API data is server state and belongs in TanStack Query (cache + refetch + loading states), with the store keeping only genuinely client-side UI state. (react.dev · data fetching as an ecosystem concern, community consensus 2026)
React rule of thumb from the docs: “every component that reads state gets re-rendered when it changes — so keep shared state as low as needed, and developers often pass the dispatch function down via a second context.” (react.dev · Scaling Up with Reducer and Context)

Why this matters for your mission

Your port's app shell is store-driven: the header/footer toggles, mobile menu, search overlay, and notification badges all read shell state. Translating store/shell.js is literally the “store wiring” item of the first slice. And in an interview, “how does global state work in React?” is the #1 Vue-era question — the answer here (there's no store; you lift state and share it with context; API data lives in a query layer) is the one they're listening for.
